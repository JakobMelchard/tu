## Header (20 bytes without options) — RFC 791 §3.1 [S13]

| Offset | Field | Bits | Meaning |
|---|---|---|---|
| 0 | Version | 4 | 4 |
| 0 | IHL | 4 | header length in 32-bit words; 5 = 20 bytes, max 15 = 60 |
| 1 | DSCP / ECN | 6 + 2 | QoS class; ECN bits 10/01 = ECT, 11 = congestion experienced (RFC 3168 §5 [S15]; RFC 791 calls the whole byte "Type of Service") |
| 2 | Total Length | 16 | header + payload in bytes, max 65535 |
| 4 | Identification | 16 | same for all fragments of one packet |
| 6 | Flags | 3 | bit 0 reserved, **DF** don't fragment, **MF** more fragments |
| 6 | Fragment Offset | 13 | position of this fragment's payload in units of **8 bytes** |
| 8 | TTL | 8 | decremented by every router; 0 → drop + ICMP Time Exceeded |
| 9 | Protocol | 8 | 1 ICMP, 6 TCP, 17 UDP, 41 IPv6-in-IPv4, 89 OSPF |
| 10 | Header Checksum | 16 | Internet checksum over the header only; recomputed per hop (TTL changed) |
| 12 | Source Address | 32 | |
| 16 | Destination Address | 32 | |
| 20 | Options | 0–40 | rare (record route, timestamp); padded to a multiple of 4 |

Internet checksum (RFC 1071 [S12]): one's-complement sum of 16-bit words with end-around carry, then complement. Verification: summing the header including the checksum gives 0xFFFF (i.e. `checksum(header) == 0`). It detects all single-bit errors and most bursts, but not swapped words (order-insensitive). Payload is *not* covered; TCP/UDP have their own.

RFC 1071 §3 works one sum through by hand, four ways [S12]. For the words `0001 f203 f4f5 f6f7`:

$$\texttt{0001} + \texttt{f203} + \texttt{f4f5} + \texttt{f6f7} = \texttt{2ddf0} \;\to\; \texttt{ddf0} + \texttt{2} = \texttt{ddf2}.$$

Byte-swapped input gives `f2dd`, i.e. `ddf2` swapped (byte-order independence, §2(B)); 32-bit words give `1ddf1` → `ddf2`; splitting after byte 3 gives `f201` + swap(`f0eb`) = `ddf2`. The RFC prints only these sums. The checksum field would carry the complement, $\lnot\texttt{ddf2} = \texttt{220d}$: that step is ours. `test_rfc_vectors.py::test_internet_checksum_rfc1071_section3` asserts every printed intermediate.

## Addressing

32 bits, dotted decimal. Historic classes A/B/C (/8, /16, /24 by leading bits 0, 10, 110) were replaced in 1993 by **CIDR** (Classless Inter-Domain Routing): an address plus a prefix length `a.b.c.d/n`; the first $n$ bits are the network part.

| Term | Formula (prefix $n$) |
|---|---|
| mask | $n$ ones then $32-n$ zeros: /26 → 255.255.255.192 |
| network address | address AND mask |
| broadcast | network OR NOT mask (all host bits 1) |
| usable hosts | $2^{32-n} - 2$ (network and broadcast excluded); /31 has 2 (RFC 3021 §2.1 [S15]: on a point-to-point link neither address is reserved), /32 is one host |
| number of /m subnets in a /n | $2^{m-n}$ |

Special ranges: 10/8, 172.16/12, 192.168/16 private (RFC 1918 §3 [S15]); 127/8 loopback; 169.254/16 link-local (APIPA, no DHCP); 100.64/10 **Shared Address Space** for carrier-grade NAT (RFC 6598 [S15] — note it is *not* RFC 1918 space, precisely so that a CGNAT and its customers cannot collide); 224/4 multicast (note 09); 0.0.0.0 "this host"/default route; 255.255.255.255 limited broadcast; 192.0.2/24, 198.51.100/24, 203.0.113/24 documentation (RFC 5737 [S15] — used throughout these notes, in preference to any real address).

### Worked example 1: decode 192.168.13.77/26

Host bits: $32 - 26 = 6$ → block size $2^6 = 64$ in the last octet. $77 = 64 + 13$ → block starts at 64.
- Network 192.168.13.64, broadcast 192.168.13.127, hosts .65–.126 (62), mask 255.255.255.192.
- Same subnet as 192.168.13.100? $100 \in [64, 127]$ → yes. 192.168.13.130? No (next block 128).

### Worked example 2: fixed-length subnetting

Split 192.168.0.0/24 into 4 subnets: need 2 more bits → /26, block size 64: 192.168.0.0/26, .64/26, .128/26, .192/26.

### Worked example 3: VLSM

10.0.0.0/24 for departments needing 60, 25, 10 and 2 hosts. Allocate largest first, each on its natural boundary:

| Need | Hosts incl. net+bcast | Prefix | Block |
|---|---|---|---|
| 60 | 64 | /26 | 10.0.0.0 – .63 |
| 25 | 32 | /27 | 10.0.0.64 – .95 |
| 10 | 16 | /28 | 10.0.0.96 – .111 |
| 2 | 4 | /30 | 10.0.0.112 – .115 |

Remaining 10.0.0.116–.255 free. (Wrong order, e.g. the /30 first at .0, would force the /26 to start at .64 and waste .4–.63.)

### Route aggregation

10.0.0.0/24 and 10.0.1.0/24 → 10.0.0.0/23 (they differ only in bit 24). 10.0.1.0/24 and 10.0.2.0/24 do **not** aggregate (bits 23–24 are 01 and 10). Aggregation is what keeps the global routing table (~1M IPv4 prefixes) manageable; see note 06 for longest-prefix match.

## Forwarding decision at a host

`dst AND mask == my_network` → deliver directly (ARP for dst); else send to the default gateway (ARP for gateway). The packet's IP destination is unchanged in both cases; only the frame's destination MAC differs.

## Fragmentation

Each link has an **MTU** (Ethernet 1500). A router that must forward a packet larger than the outgoing MTU splits the *payload* into pieces that are multiples of 8 bytes (except the last), copies the header (same Identification, MF = 1 on all but the last, Fragment Offset = payload position / 8), recomputes length and checksum — RFC 791 §3.2, "Fragmentation" [S13]. **Only the destination host reassembles** (waits for all pieces, timer ~30 s; any lost fragment loses the whole packet). If DF is set the router drops and returns ICMP type 3 code 4 "fragmentation needed"; RFC 1191 [S15] added the next-hop MTU to that message and defined **Path MTU Discovery** on top of it: hosts set DF and adapt. Firewalls dropping ICMP break PMTUD ("black hole": small packets pass, big ones vanish).

Worked: 1044-byte packet (20 + 1024) over MTU 576: payload per fragment $\lfloor(576-20)/8\rfloor \cdot 8 = 552$.

| Fragment | Total length | MF | Offset (×8) |
|---|---|---|---|
| 1 | 572 | 1 | 0 |
| 2 | 20 + 472 = 492 | 0 | 69 (= 552/8) |

IPv6 routers never fragment (note 04).

## TTL

Set by the sender (Linux 64, Windows 128, network gear 255 — implementation choices, not RFC 791, which only recommends a maximum lifetime), decremented per router; a router receiving TTL 1 drops and sends ICMP type 11 [S13]. Purpose: kill packets caught in a routing loop. **traceroute** exploits it: probes with TTL 1, 2, 3, … elicit Time Exceeded from each hop; the final hop answers with ICMP Port Unreachable (UDP probes) or Echo Reply (ICMP probes). From a trace you can infer distance: a received TTL of 57 from a Linux host means 7 hops.

## ICMP (RFC 792 [S13]) — the control plane of IP

Carried in IP (protocol 1): type, code, checksum, then type-specific data; error messages quote the offending IP header + the first 64 **bits** (8 bytes) of its payload — RFC 792's wording — which is exactly enough to recover the source and destination ports, so the host can match the error to a socket.

| Type/code | Meaning | Who sends |
|---|---|---|
| 0 / 8 | echo reply / request (ping) | hosts |
| 3 | destination unreachable: 0 net, 1 host, 3 port, 4 fragmentation needed (DF), 13 admin prohibited | routers, hosts |
| 11 | time exceeded (0 TTL in transit, 1 reassembly) | routers |
| 5 | redirect (better gateway on the same subnet) | routers |
| 12 | parameter problem | |

ICMP errors are never sent in response to ICMP errors, broadcasts or fragments other than the first (no storms).

## NAT (RFC 3022 [S15], "NAPT")

A router with one public address rewrites (private src IP, src port) ↔ (public IP, new port) and keeps the mapping in a table; return packets are translated back. It recomputes IP and TCP/UDP checksums — in practice incrementally, by RFC 1624's equation 3 [S11], because only the address and port words changed. Motivation: IPv4 exhaustion. *(unsourced: "RIPE NCC ran out of its free pool in November 2019" was not checked against a RIPE NCC announcement in this pass; it is the commonly cited date.)* Costs: breaks the end-to-end principle (inbound connections need port forwarding or hole punching: STUN/TURN/ICE), protocols that carry addresses in the payload need ALGs (FTP, SIP) — RFC 3022 §4.1 says so explicitly — a NAT keeps per-flow state (timeouts drop idle UDP mappings), and it is not a security feature (a stateful firewall is). CGNAT adds a second layer at the ISP, in 100.64/10 [S15].

## Pitfalls

- Header checksum covers the header only; a corrupted payload passes IP and is caught (maybe) by TCP/UDP.
- Fragment Offset counts 8-byte units; Total Length in a fragment is the fragment's length, not the original.
- A /30 has 2 hosts and a /31 also 2 (no broadcast); /32 host route.
- 192.168.0.255/23 is a valid host address: the block is 192.168.0.0–192.168.1.255 and its broadcast is 192.168.1.255. An all-ones last octet is a broadcast only for /24 and longer prefixes.
- TTL is not time; it is a hop count.
- Private addresses are routable inside a network; they are only not routed *on the public Internet* (by convention/filtering).

## Exam-style questions

1. *172.16.35.200/20: network, broadcast, number of hosts?* /20 → third octet block size 16: $35 = 32 + 3$ → 172.16.32.0, broadcast 172.16.47.255, $2^{12}-2 = 4094$ hosts.
2. *Why must the header checksum be recomputed at every router, and why is this cheap?* TTL changes; incremental update, RFC 1624 equation 3 [S11]: $\mathrm{HC}' = \sim(\sim\mathrm{HC} + \sim m + m')$ in one's-complement arithmetic, two additions instead of a ten-word sum. The obvious-looking RFC 1141 equation 2, $\mathrm{HC}' = \mathrm{HC} + m + \sim m'$, is **wrong**: RFC 1624 §4 exhibits a case where it returns 0xFFFF, which is negative zero and can never be a valid header checksum. `inet_checksum.incremental_checksum_update` implements equation 3 and `test_rfc_vectors.py` reproduces the RFC's numbers ($m = \mathtt{0x5555} \to \mathtt{0x3285}$, rest $\mathtt{0xCD7A}$, $\mathrm{HC} = \mathtt{0xDD2F}$, $\mathrm{HC}' = \mathtt{0x0000}$).
3. *A 3000-byte UDP datagram (IP total length 3020) enters a 1500-MTU link. Fragments?* Payload per fragment 1480: three fragments with offsets 0, 185, 370, lengths 1500, 1500, 60 (20 + 40), MF = 1, 1, 0. Only the first contains the UDP header.
4. *A host behind NAT opens two connections to the same server port 80 from source ports 5000 and 5001; another host behind the same NAT also uses 5000. How does the NAT keep them apart?* By assigning distinct public ports (e.g. 40000, 40001, 40002) and keying the table on (private IP, private port, dst IP, dst port).
5. *traceroute shows `* * *` for hop 5 but later hops answer. Is hop 5 down?* No: it forwards but does not send (or rate-limits) ICMP Time Exceeded, or a firewall drops it. Data still passes, as the later hops prove.
