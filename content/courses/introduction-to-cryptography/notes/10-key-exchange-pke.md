Public-key cryptography removes the need for a pre-shared secret: encrypt with a
*public* key, decrypt with a matching *private* one. This note covers key
exchange (Diffie-Hellman), the two flagship encryption families (RSA, ElGamal),
why the "textbook" versions are broken, and how real systems fix them (OAEP,
hybrid encryption). Security reduces to the assumptions of note 09.

## Diffie-Hellman key exchange

The paper that started public-key cryptography, *New Directions in Cryptography*
[S51], which lecture 11 names by title [S8]. Public parameters: a prime-order group $G=\langle g\rangle$ (a safe-prime
subgroup, note 09). Alice picks secret $x$, sends $g^x$; Bob picks $y$, sends
$g^y$; both compute the shared value $g^{xy}=(g^y)^x=(g^x)^y$ and hash it to a
key. Code: `dh.keypair`, `dh.shared_secret`; `test_dh.py` checks agreement and
that public keys lie in the order-$q$ subgroup.

- **Passive security** rests on **DDH**: the transcript $(g^x,g^y)$ plus the key
  $g^{xy}$ is indistinguishable from $(g^x,g^y,g^z)$ with random $z$, so the key
  looks random to an eavesdropper. (CDH would only hide the *whole* key, not
  guarantee it looks random — DDH is the right assumption.)
- **No authentication.** DH gives a shared key but not *with whom*. An active
  attacker runs separate exchanges with each side — the **man-in-the-middle**:
  `dh.mitm_demo` shows Alice's key matching the attacker's, Bob's matching the
  attacker's, and Alice and Bob sharing *nothing*
  (`test_dh.py::test_mitm_breaks_agreement`). Fix: authenticate the exchange with
  signatures (note 11) or a password — this is what TLS does.

## Public-key encryption and its games

A PKE scheme: $\mathsf{Gen}\to(pk,sk)$, $\mathsf{Enc}_{pk}(m)$, $\mathsf{Dec}_{sk}(c)$. The CPA
game is as in note 06 **but the adversary is given $pk$** — so it can encrypt
freely without an oracle. Immediate consequence, exactly as before:
**every CPA-secure PKE must be randomised.** CCA adds a decryption oracle
(forbidden on the challenge) and is the notion real systems must meet.

## Textbook RSA and why it is insecure

The original construction [S52], unchanged in form since 1978. Keygen: $N=pq$, choose $e$ with $\gcd(e,\varphi(N))=1$, set $d=e^{-1}\bmod\varphi(N)$.
$\mathsf{Enc}(m)=m^e\bmod N$, $\mathsf{Dec}(c)=c^d\bmod N$. Correct by Euler:
$c^d=m^{ed}=m^{1+k\varphi(N)}\equiv m$. Code: `rsa.keygen`, `encrypt`, `decrypt`,
plus CRT decryption `rsa.decrypt_crt` (note 09). One-wayness rests on the **RSA
assumption**.

Textbook RSA is **deterministic**, so not CPA-secure, and its algebraic
structure enables devastating attacks (all in `rsa.py`, all tested):

- **Malleability / homomorphism:** $(m\cdot s)^e = m^e\cdot s^e$, so multiplying
  the ciphertext by $s^e$ multiplies the plaintext by $s$ — without the key.
  `rsa.malleability_demo` turns $\mathsf{Enc}(42)$ into $\mathsf{Enc}(126)$. Breaks CCA.
- **Small-message / small-$e$:** if $m^e < N$ (e.g. $e=3$, short $m$), no modular
  reduction happens and $m=\sqrt[e]{c}$ over the integers. `rsa.small_message_attack`.
- **Hastad broadcast:** the same $m$ sent to $e$ recipients with exponent $e$ and
  coprime moduli; CRT gives $m^e \bmod \prod N_i$, and since $m^e<\prod N_i$, an
  integer $e$-th root recovers $m$. `rsa.small_e_attack`.
- **Common modulus:** same $N$, same $m$, coprime $e_1,e_2$; Bezout $ae_1+be_2=1$
  gives $c_1^a c_2^b = m$. `rsa.common_modulus_attack`. (Moral: never share an RSA
  modulus across users.)
- **Shared prime factor:** two moduli $N_1,N_2$ generated by a faulty RNG happen
  to share one prime. Then $p=\gcd(N_1,N_2)$ — *one Euclid run, no factoring* —
  and both private keys follow. This is question 4b of the 26 January 2024 final
  [S12], and it is not a thought experiment: Heninger et al. factored a
  measurable share of the public TLS and SSH RSA keys on the internet this way,
  because embedded devices generated keys before their entropy pool had filled
  [S47]. `rsa.shared_prime_attack`.

Note how much weaker the *assumption* is in the last one. Common modulus needs a
deliberate design error; a shared prime needs only a bad boot sequence on one
device in a batch.

## Padding RSA: PKCS #1 v1.5, then OAEP

Plain RSA is unusable, so the standard pads. Lecture 12 walks the two versions
in order [S8], and the history is the lesson.

### PKCS #1 v1.5 (1993) — and why it is not enough

Randomise by prefixing random non-zero padding:
$\mathrm{EM} = \texttt{0x00}\,\|\,\texttt{0x02}\,\|\,PS\,\|\,\texttt{0x00}\,\|\,m$
with $PS$ at least 8 random non-zero octets [S20 sec. 7.2]. Randomised, so no
longer trivially CPA-broken.

It is still **not CCA-secure**. A decryptor that reveals whether the leading
octets were `00 02` is an oracle, and Bleichenbacher's "million message attack"
[S42] uses it to narrow the plaintext interval by repeated multiplication with
chosen factors — the public-key twin of note 06's padding oracle, and the reason
TLS 1.3 removed RSA key transport altogether (note 12). RFC 8017 keeps v1.5 only
for compatibility and its security considerations say not to use it for new
designs [S20].

## RSA-OAEP, as RFC 8017 sec. 7.1 actually defines it

**Optimal Asymmetric Encryption Padding** [S39] is what PKCS #1 v2.0 adopted and
RFC 8017 (v2.2) specifies [S20]. Lecture 12 draws it as *two rounds of a Feistel
network* over (seed, $m\|$padding) with hash-based mask generation [S8]. That
picture is right and incomplete; the standard adds two things the picture omits,
and both are load-bearing.

Write $k$ for the modulus length in octets, $hLen$ for the hash output length
(32 for SHA-256), $L$ for an optional **label** (default the empty string).

**Encoding (sec. 7.1.1 step 2):**

1. $lHash := \mathrm{Hash}(L)$ &nbsp;&nbsp;*(the first omitted piece)*
2. $PS := \texttt{0x00}^{\,k-|m|-2hLen-2}$
3. $DB := lHash \,\|\, PS \,\|\, \texttt{0x01} \,\|\, m$ &nbsp;&nbsp;*(the second: the `0x01` separator)*
4. $seed \gets \{0,1\}^{8\cdot hLen}$ uniform
5. $maskedDB := DB \oplus \mathrm{MGF}(seed,\ k-hLen-1)$
6. $maskedSeed := seed \oplus \mathrm{MGF}(maskedDB,\ hLen)$
7. $EM := \texttt{0x00} \,\|\, maskedSeed \,\|\, maskedDB$

then $c := \mathrm{I2OSP}(\mathrm{EM}^{\,e} \bmod N,\ k)$. Steps 5-6 are the two
Feistel rounds of the lecture slide.

**MGF1 (appendix B.2.1)** is the mask generation function:
$\mathrm{MGF}(Z,\ell)$ is the first $\ell$ octets of
$\mathrm{Hash}(Z\|\langle 0\rangle_4)\,\|\,\mathrm{Hash}(Z\|\langle 1\rangle_4)\,\|\cdots$,
counter big-endian on four octets. Note it is a *prefix family*: a shorter mask
is a prefix of a longer one (`test_oaep.py::test_mgf1_is_a_prefix_family`).

**Decoding (sec. 7.1.2 step 3)** reverses the masks and then checks **three**
things: the leading octet is `0x00`, the recovered $lHash'$ equals
$\mathrm{Hash}(L)$, and $DB$ contains a `0x01` octet terminating the zero
padding. Any failure is "decryption error".

Three points the teaching outline loses, in order of importance:

1. **The three checks are what make it CCA-secure.** Without the $lHash$
   comparison and the `0x01` separator, a mauled ciphertext decodes to *some*
   string and is returned rather than rejected. `all-or-nothing` describes the
   scrambling; the format check is what converts scrambling into rejection.
   `test_oaep.py` replays 19 published malformed ciphertexts that each trip one
   of these branches [S24].
2. **RFC 8017 sec. 7.1.2 step 3(g) forbids distinguishing the failures** — same
   error, no timing difference. Manger's attack [S41] recovers the plaintext in
   about $\lvert N\rvert$ oracle queries if the implementation lets you tell
   "integer too large" apart from "bad padding". This is why `oaep.py` raises one
   exception type and says in its docstring that it is still not constant-time.
3. **The label $L$ is authenticated, not encrypted.** It binds a context (a
   session id, a purpose string) into the ciphertext for free; decrypting under
   the wrong label fails (`test_oaep.py::test_label_is_authenticated`).

**Size.** $|m| \le k - 2hLen - 2$: for a 2048-bit modulus and SHA-256 that is
$256-64-2 = 190$ octets. RSA-OAEP is therefore used to wrap a symmetric key, not
to encrypt data — which is the hybrid encryption below.

**Security, stated carefully (background — lecture 13a lists public-key security
proofs as not covered [S8]).** The original paper claimed IND-CCA2 for *any*
one-way trapdoor permutation [S39]. **Shoup showed that proof is flawed** and
that the generic claim is false [S40]. Fujisaki, Okamoto, Pointcheval and Stern
then proved the *RSA instance specifically* CCA-secure in the random-oracle model
under the RSA assumption, with a loose reduction [S40]. So the correct sentence
is: **RSA-OAEP is CCA-secure in the ROM under the RSA assumption** — not "OAEP
makes any trapdoor permutation CCA-secure".

Code: [`../src/py/oaep.py`](../src/py/oaep.py) implements sec. 4.1, 4.2, 5.1.1,
5.1.2, 7.1.1, 7.1.2 and B.2.1 line by line;
[`../src/py/test_oaep.py`](../src/py/test_oaep.py) checks it against 37 published
vectors [S24] and against the `cryptography` library in both directions.

## ElGamal encryption

Over a prime-order group $G=\langle g\rangle$ (note 09). Keygen: secret $x$,
public $h=g^x$. Encrypt $m\in G$ with fresh $y$:
$$\mathsf{Enc}_{h}(m) = (c_1,c_2) = (g^y,\ m\cdot h^y).$$
Decrypt: $c_2 / c_1^x = m\cdot h^y / g^{xy} = m$. Code: `elgamal.encrypt`,
`decrypt`; randomised, so encrypting $m$ twice gives different ciphertexts
(`test_elgamal.py`). **$m\in G$ is not a formality**: in the order-$q$ subgroup
of $\mathbb Z_p^*$ every $h^y$ is a quadratic residue, so for $m\notin G$ the
Legendre symbol of $c_2$ equals that of $m$ and one bit leaks
(`test_elgamal.py::test_messages_outside_the_group_break_ind_cpa`).
`elgamal.encode` maps $m\in[1,q]$ into $G$ ($m$ or $p-m$, whichever is a
residue) and `decode` inverts it.

**Theorem.** ElGamal is IND-CPA **iff DDH holds** in $G$.
*Proof ($\Leftarrow$), the reduction.* Let $\mathcal A$ break IND-CPA with
advantage $\varepsilon$. Build a DDH distinguisher $\mathcal B(g^a,g^b,T)$:
1. Set $pk=h=g^a$ and give it to $\mathcal A$.
2. Receive $(m_0,m_1)$; pick $\beta\gets\{0,1\}$; return the challenge
   $c=(g^b,\ m_\beta\cdot T)$.
3. Output $1$ iff $\mathcal A$'s guess $\beta'=\beta$.

- If $T=g^{ab}$ (real DH tuple): $c=(g^b, m_\beta\cdot h^b)$ is a *genuine*
  ElGamal ciphertext, so $\mathcal A$ sees the real game and $\Pr[\mathcal B\to1]=
  \tfrac12+\varepsilon$.
- If $T=g^z$, $z$ random: $m_\beta\cdot g^z$ is uniform in $G$, independent of
  $\beta$ (multiplying by a uniform group element is a one-time pad *in the
  group*), so $\Pr[\mathcal B\to1]=\tfrac12$.

Hence $\mathsf{Adv}^{DDH}_{\mathcal B}=\varepsilon$; DDH-hardness forces $\varepsilon$
negligible. ($\Rightarrow$) is the mirror reduction. $\square$ This is the
cleanest DDH reduction in the course — study its shape for note 13.

**Malleability / re-randomisation.** ElGamal is homomorphic:
$(c_1,c_2\cdot s)$ decrypts to $m\cdot s$ (`elgamal.malleability_demo`), and
multiplying by an encryption of $1$ gives a fresh encryption of the *same*
message (`elgamal.rerandomize`). Useful (mix-nets, e-voting) but means ElGamal
is **not CCA-secure** as-is.

## Hybrid encryption (KEM/DEM)

Public-key operations are slow and restrict message size; symmetric ones are
fast and arbitrary-length. **Hybrid encryption** combines them: use PKE to
encapsulate a fresh symmetric key $k$ (the **KEM**), then encrypt the actual
message under $k$ with authenticated symmetric encryption (the **DEM**):
$$c = \big(\mathsf{Enc}^{\mathrm{pub}}_{pk}(k),\ \mathsf{AE}_k(m)\big).$$
**KEM/DEM composition theorem:** a **CCA-secure** KEM plus a CCA-secure
(authenticated) DEM gives a CCA-secure hybrid PKE. This is how TLS, PGP and age
actually encrypt: RSA-OAEP or ECDH for the key, AES-GCM for the data. It also
removes RSA's length limit and the need to encode messages as group elements.

> **Both halves must be CCA-secure, and this is an exam question** [S12].
> Instantiate the KEM with *plain ElGamal* — CPA-secure but re-randomisable — and
> the composition is broken however good the DEM is. Given the challenge
> $\big((c_1,c_2),\ \mathsf{Enc}'_k(m)\big)$, multiply $c_1$ by $g^s$ and $c_2$ by
> $h^s$: the KEM part still encapsulates the same $k$, the DEM part is untouched,
> and the result is a *different* ciphertext, so the CCA decryption oracle will
> answer it and hand back $m$. One query, advantage $1/2$.
> `elgamal.hybrid_encrypt` and `elgamal.hybrid_cca_attack`.

### DHIES / ECIES — the fix

Lecture 12 gives the repair [S8]: do not encapsulate an independent $k$, derive
the DEM key from the *ciphertext element and* the DH value:

$$c = \Big(g^y,\ \mathsf{Enc}'_{H(g^y,\ h^y)}(m)\Big).$$

Now $c_1$ is an input to the key derivation, so mauling it changes the key and
the DEM's authentication tag fails instead of decrypting. Over an elliptic curve
the same scheme is **ECIES**. `elgamal.dhies_encrypt` / `dhies_decrypt`, and
`test_elgamal.py::test_dhies_resists_the_same_attack`. CCA-secure in the ROM
under a hashed-DH (gap-DH) assumption — background, per lecture 13a [S8].

## CCA security (idea)

CPA is not enough against active attackers (the RSA malleability and padding
oracles are CCA breaks). Achieving CCA in the public-key world:
- **RSA:** OAEP (ROM).
- **DH/ElGamal:** the **Cramer-Shoup** cryptosystem — CCA-secure under DDH in the
  *standard model* (no ROM), by adding a hash-based consistency check that makes
  the decryption oracle useless to the attacker. (Named/idea only.)
- **Generic:** hybrid KEM/DEM with a CCA-secure DEM (encrypt-then-MAC / GCM).

## Worked example

*Show textbook RSA fails IND-CPA with a one-query attack.* $\mathcal A$ is given
$pk=(N,e)$, outputs $m_0\ne m_1$, receives $c=m_b^e$. Because encryption is
deterministic and $\mathcal A$ has $pk$, it simply computes $m_0^e\bmod N$ itself
and outputs $0$ iff $c=m_0^e$. Always correct: advantage $1/2$. The *only* fix is
randomisation (OAEP). $\square$

## Pitfalls

- **Textbook RSA/ElGamal are teaching objects.** Never encrypt real data with
  them; use OAEP / hybrid / Cramer-Shoup.
- **Unauthenticated DH $\Rightarrow$ MITM.** Always authenticate the key exchange.
- **Never share an RSA modulus** (common-modulus attack); use independent $N$ per
  user and $e=65537$.
- **DDH must actually hold** — use the prime-order subgroup, encode messages *into*
  $G$ (ElGamal needs $m\in G$, not an arbitrary bit string).
- **Homomorphism is a double-edged sword:** great for protocols, fatal for CCA if
  unaddressed.
- **Fresh randomness per encryption** ($y$ in ElGamal, seed in OAEP); reuse
  collapses to the deterministic (broken) case.

## Exam-style questions

**Q1** *(F24 4b [S16]).* Why is the security notion for public-key encryption
called "CPA-security" when the adversary is given no encryption oracle? —
Because it has $pk$, so it *is* its own encryption oracle: it can encrypt any
message it likes, as often as it likes, with fresh randomness. Handing it an
oracle would add nothing. The same observation forces the conclusion that every
CPA-secure PKE is randomised — a deterministic one loses to "encrypt $m_0$
yourself and compare".

**Q2** *(F23 5a [S12]).* For ElGamal with
$\mathsf{Gen}(1^n)$: $x\gets\mathbb Z_q$, $pk := g^x$, $sk := x$, and
$\mathsf{Enc}_{pk}(m)$: $r\gets\mathbb Z_q$, return $(g^r,\ pk^r\cdot m)$ — give
$\mathsf{Dec}$ and argue correctness. —
$\mathsf{Dec}_{sk}(c_1,c_2) := c_2\cdot c_1^{-x}$. Correctness:
$c_1^{x} = (g^r)^x = (g^x)^r = pk^r$, so
$c_2\cdot c_1^{-x} = pk^r m \cdot pk^{-r} = m$. The inverse exists because
$\mathbb G$ is a group (every element, $1$ included, has one); since
$c_1^q = 1$ in a group of order $q$, computing it is one exponentiation,
$c_1^{-x} = c_1^{q-x}$.

**Q3** *(F23 5b [S12]).* Let $(\mathsf{Gen},\mathsf{Enc},\mathsf{Dec})$ be
ElGamal and $(\mathsf{Gen}',\mathsf{Enc}',\mathsf{Dec}')$ a **CCA-secure**
private-key scheme with key space $\mathbb G$. Show that the hybrid
$\mathsf{Enc}_{pk}(m) = \big(\mathsf{Enc}_{pk}(k),\ \mathsf{Enc}'_k(m)\big)$,
$k\gets\mathbb G$, is not CCA-secure. — Receive the challenge
$\big((c_1,c_2),\, d\big)$. Pick $s\gets\mathbb Z_q$ and submit
$\big((c_1 g^s,\ c_2 h^s),\, d\big)$ to the decryption oracle. It differs from
the challenge, so the query is legal; but $(c_1g^s, c_2h^s)$ is a re-randomised
encryption of the *same* $k$, so the oracle derives the same DEM key and returns
$m$. Output the bit matching $m$. Advantage $1/2$, one query, and the DEM's
CCA-security is never touched — the composition theorem needs the **KEM** to be
CCA-secure, which plain ElGamal is not.

**Q4** *(F23 4b [S12]).* $(N_1,e_1)$ and $(N_2,e_2)$ are RSA public keys whose
moduli were generated so that they share one prime factor. Recover both secret
keys efficiently. — $p := \gcd(N_1,N_2)$, by Euclid, in $O(\log^2 N)$ bit
operations. Then $q_i := N_i/p$, $\varphi(N_i) = (p-1)(q_i-1)$,
$d_i := e_i^{-1}\bmod\varphi(N_i)$. No factoring algorithm is involved: the
shared prime *is* the GCD. Moral: RSA key generation is only as good as the
entropy behind it, and the failure is silent — both moduli look perfectly
ordinary in isolation [S47]. `rsa.shared_prime_attack`.

**Q5** *(ours — RSA padding has not appeared on a public paper, but lecture 12
spends two slides on it [S8], so treat it as fair game.)* Alice encrypts a
128-bit AES key under RSA-2048 with OAEP-SHA-256. Bob's decryption code returns
"integer too large" when the RSA decryption does not fit in $k-1$ octets (its
leading octet is not `0x00`) and "bad padding"
when the format check fails. What is wrong, and what is the fix? — The two error
messages are a Manger oracle [S41]. The distinction tells the attacker whether
the decrypted integer is below $2^{8(k-1)}$, which is a comparison against a
known threshold; multiplying the ciphertext by $s^e$ and binary-searching on $s$
recovers the plaintext in about 2048 queries — far cheaper than Bleichenbacher's
million-message attack on v1.5. The fix is RFC 8017 sec. 7.1.2 step 3(g): one
indistinguishable error for every failure, and no timing difference either, which
in practice means constant-time comparisons and no early returns.

**Q6** *(ours; the DH man-in-the-middle is on no past paper but underpins
note 12).* Why does the passive security of Diffie-Hellman need DDH rather than
CDH, and what changes if the shared key is hashed? — CDH says the attacker
cannot *compute* $g^{xy}$; it does not say $g^{xy}$ looks random, and it is
consistent with CDH that half the bits of $g^{xy}$ are easy to predict. Using it
as a key requires indistinguishability from uniform, which is exactly DDH. If the
key is $H(g^{xy})$ with $H$ modelled as a random oracle, CDH suffices — the
hashed-DH assumption — because the only way to learn anything about $H(g^{xy})$
is to query $H$ at $g^{xy}$, which is the CDH problem. This is why real protocols
always run the DH value through a KDF [S34] and never use it raw.
