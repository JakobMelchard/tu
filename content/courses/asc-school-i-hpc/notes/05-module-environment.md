## What a module is

A cluster has dozens of compilers, MPI libraries and numerical libraries in
several versions each, installed side by side under paths like
`/gpfs/opt/sw/zen/spack-0.19.0/opt/spack/linux-almalinux8-zen3/...`. A **module**
is a small Tcl file that, when loaded, prepends the right directories to `PATH`,
`CPATH`, `LIBRARY_PATH`, `LD_LIBRARY_PATH`, `MANPATH` and friends, and records
what it did so it can be undone [S10] [S19]. Nothing is installed or copied;
`module load` only changes *this shell*. `module` is a shell function that evals
the output of the modules binary, which is why it can change your environment at
all.

## The commands, as ASC documents them

```bash
module --help                      # general help
module avail                       # everything visible now
module avail openmpi               # filter by name (case sensitive: Matlab, Mathematica)
module avail -t | grep -i mpi      # terse, greppable
module load  <name>                # add to the session (synonym: module add)
module list                        # what is loaded now (flushed at logout)
module list -t                     # terse
module show  <name>                # the modulefile: the paths it prepends. No need to load it first.
module rm <name> ...               # remove (synonym: module unload)
module purge                       # remove everything - first line of every job script
```

Source: the ASC modules slide and the identically-worded documentation page
[S10] [S19].

### Names are long, and you must type the whole thing

Module names are Spack specs: `<package>/<version>-<compiler>-<version>-<hash>`.

```
skylake$ module load openmpi/4.1.4-gcc-12.2.0-xt53foa      # works
skylake$ module load openmpi/4.1.4
ERROR: Unable to locate a modulefile for 'openmpi/4.1.4'
```

There is no default version to fall back on, so *"always state the whole line"*
[S10] [S19]. The corollary is pleasant: your job scripts are automatically
reproducible, because you cannot write an unpinned `module load gcc`.

The hash differs per CPU architecture, so the same package has a different name
on each cluster [S10] [S19]:

```
skylake$   module load python/3.11.3-gcc-12.2.0-rtzvjko
zen$       module load python/3.11.3-gcc-12.2.0-hn7p65z
cuda-zen$  module load python/3.9.15-gcc-12.2.0-dnctq7y
```

`skylake`, `zen` and `cuda-zen` are the **software environments**, and the name
of the one you are in is the first field of the ASC prompt [S7] [S10]. They are
why `module avail aocc` finds something on `zen` and nothing on `skylake`.

### Dependencies

`module load` of a leaf package pulls its prerequisites in and tells you so:

```
zen$ module load py-numpy/1.24.3-gcc-12.2.0-muackhh
Loading py-numpy/1.24.3-gcc-12.2.0-muackhh
  Loading requirement: netlib-lapack/3.10.1-gcc-12.2.0-4qrxbdw
      python/3.9.15-gcc-12.2.0-my6jxu2
      py-setuptools/63.0.0-gcc-12.2.0-jru4czh
```

`module load --auto <name>` forces automatic dependency handling;
`export MODULES_AUTO_HANDLING=1` (or `=0`) in `~/.bashrc` sets it permanently
[S10] [S19]. This is *not* Lmod's hierarchy: nothing is hidden from `module
avail` until you load a compiler. Everything is visible all the time, which is
why the useful search is `module avail -t | grep …` rather than `module spider`.

## Compilers and MPI on the ASC systems

The compiling deck is marked **OUTDATED** by ASC itself and dropped from the
day's running order [S8]; its hashes are Spack 0.19 and will not resolve today.
The *shape* of the tables is still right and is not documented anywhere else, so
it is reproduced here — with that caveat — from [S10].

| CPU environment | login nodes | partitions | compilers | fastest, per ASC |
|---|---|---|---|---|
| `skylake` (VSC-4) | l40–l4x | `skylake_0096`, `_0384`, `_0768`, and `cascadelake_0384` | gnu, intel / oneapi / dpcpp | **intel** |
| `zen` (VSC-5) | l50–l56 | `zen3_0512`, `zen3_1024`, `zen3_2048`, `zen3_0512_a100x2`, `zen2_0256_a40x2` | gnu, intel/oneapi, **aocc** | **aocc** |
| `cuda-zen` (VSC-5 GPU) | l50–l56 | GPU partitions | gnu, intel/oneapi, **nvhpc** (no aocc — it does not work with CUDA) | — |

| language | Intel | GNU | AOCC |
|---|---|---|---|
| C | `icx` | `gcc` | `clang` |
| C++ | `icpx` | `g++` | `clang++` |
| Fortran | `ifx` | `gfortran` | `flang` |

| | Intel oneAPI | Intel classic | Open MPI |
|---|---|---|---|
| module | `intel-oneapi-mpi` | `intel-oneapi-mpi` | `openmpi` |
| compiler module | `compiler/latest` | `intel/19` | any |
| C | `mpiicc` | `mpicc` / `mpigcc` | `mpicc` |
| C++ | `mpiicpc` | `mpicxx` / `mpigxx` | `mpic++` / `mpicxx` |
| Fortran | `mpiifort` | `mpifc` / `mpiifort` | `mpifort` |

MPICH, MVAPICH and MVAPICH2 are installed too [S10]. Architecture flags from the
same deck: `-O2 -march=skylake` on VSC-4, `-march=znver3` on VSC-5 CPU nodes,
`-march=znver2` on the A40 GPU nodes — **the A40 partition is the only Zen2
hardware on VSC-5, so a `znver3` binary faults there** [S10]. Intel's equivalent
is `-O3 -xHost`. OpenMP: `-qopenmp` (Intel), `-fopenmp` (GNU, AOCC).

```bash
module purge                                              # always
module load compiler/latest
module load intel-oneapi-mpi/2021.7.1-intel-2021.7.1-fzg6q4x
mpiicc -O3 -xHost hello-mpi.c -o hello-mpi
mpiicc -show          # what the wrapper really calls (Open MPI: mpicc --showme)
mpirun -np 2 ./hello-mpi
```

`mpicc` is a **wrapper**: the toolchain compiler plus `-I` for `mpi.h` and
`-L -lmpi` for the library. Because linking is dynamic, the job script must load
the same modules as the build; `module list` at the top of a job puts the proof
in the `.out` file. Optimisation flags belong to you, not to the wrapper.

## The other three ways to get software

The cluster-intro day spends five minutes each on these [S8]; they are not
examinable but they are how you will actually install things.

- **Spack** is the package manager the modules are generated from, so
  `spack find -l mpi` and `module avail mpi` usually show the same things
  [S10]. On GPU nodes ASC's own example uses `spack load cuda@11.8.0%gcc@9.5.0/ananl33`
  directly instead of a module [S9].
- **EESSI** is a shared, CernVM-FS-distributed software stack (the "European
  Environment for Scientific Software Installations"), mounted read-only and
  identical across sites [S19].
- **Conda** for Python stacks, with the environment in `$HOME` — which is the
  one research-adjacent thing ASC explicitly allows in `$HOME` [S19]. A
  `mpi4py` for the block-3 labs must be built against the site MPI, not
  installed as a PyPI wheel.

## Pitfalls

- Typing `module load openmpi/4.1.4` and expecting a default: there is none
  [S10] [S19].
- Copying a `module load` line from the 2022 compiling deck: the hash is gone.
  Re-run `module avail` and copy the current line.
- Loading modules in `~/.bashrc`: the documentation calls customising `.bashrc`
  a cause of failing jobs and recommends against it outright [S19]. Load in the
  job script, after `module purge`.
- Building on a `zen` login node and running on `zen2_0256_a40x2`: `-march=znver3`
  against Zen2 hardware [S10].
- Mixing a `gcc`-built library with an `intel`-built MPI: link errors or silent
  ABI breakage. Stay in one toolchain — the module names make the toolchain
  visible, use that.
- Reaching for `module spider`, `ml` or `module save`: Lmod commands, not
  available here [S17] [S18].
- `pip install` into the site Python without a conda env or venv: `--user`
  packages then shadow module packages for every project you have.

## For contrast: what Lmod would give you

Most other HPC centres run **Lmod** [S18]. There, modules are Lua, `MODULEPATH`
is **hierarchical** (MPI modules appear only after a compiler is loaded),
`module spider name` finds hidden modules and prints the prerequisites, `module
keyword` searches descriptions, `module swap` exchanges a compiler and reloads
dependants, `module save`/`restore` keep named collections, `ml` is shorthand,
and an unversioned `module load gcc` gives you whatever is currently marked
`(D)` — which is the reason Lmod sites tell you to pin versions and ASC does not
have to. If you move to a site where `module avail` looks suspiciously empty,
that is the hierarchy, and `module spider` is the way out.

## Questions

Our questions — this course has no exam and no past papers
([00](00-exam-focus.md)). Q1–Q3 restate things the ASC modules exercise actually
asks [S10].

1. **`module avail python` lists three entries with different hashes on VSC-4
   and VSC-5. Why, and which do you load?** The modules are generated per
   software environment (`skylake`, `zen`, `cuda-zen`) by Spack, and the hash
   encodes the build, so the same version has different names per architecture.
   Load the full line printed by `module avail` **on the machine you will run
   on** [S10] [S19].
2. **What does `module load py-matplotlib/3.6.2-gcc-12.2.0-c7hrkux` print, and
   how do you find out which numpy it needs without loading it?** It prints a
   "Loading requirement:" list. `module show py-matplotlib/3.6.2-…` shows the
   modulefile without loading, and the requirement list names the `py-numpy`
   build [S10].
3. **Find an Open MPI built with AOCC on VSC-5.** `module avail openmpi` on a
   `zen` login node; the AOCC builds carry `-aocc-` in the name
   (e.g. `openmpi/4.1.4-aocc-4.0.0-…`) [S10].
4. **Why does every ASC job script start with `module purge`?** So the job's
   environment is defined entirely by the script and not by whatever was loaded
   in the submitting shell — ASC recommends it for reproducibility [S10] [S19]
   and puts it in every sample script [S9].
5. **You get `error while loading shared libraries: libmpi.so.40` when the job
   starts, though it compiled fine. Two causes?** The job did not load the same
   MPI module as the build (most likely, after a `module purge`), or it loaded a
   different build whose path differs. `ldd ./prog` after loading the modules
   shows which library is unresolved.
6. **Why is `module spider` not the answer to "I cannot see the module I need"
   here?** Because there is no hierarchy to spider through: ASC's tree is flat
   and `module spider` is an Lmod command that does not exist on these systems.
   The right move is `module avail -t | grep -i <name>`, on the right CPU
   environment [S10] [S17].
